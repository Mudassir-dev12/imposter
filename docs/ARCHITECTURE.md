# Impostor System Architecture

## 1. System Overview

Impostor is a local-multiplayer social deduction game designed for zero-cloud, peer-to-peer Wi-Fi or portable hotspot operation. A single player acts as the game host, running both the Flutter UI client and an embedded Python server on their mobile device (Android). Other players join as WebSocket clients either via camera QR code scanning or manual IP address and room code entry.

```
       +-----------------------------------------------------------+
       |                     Host Android Device                   |
       |                                                           |
       |  +--------------------+         +----------------------+  |
       |  | Flutter Client     |         | Foreground Service   |  |
       |  | (Host UI & Lobby)  |         | & WakeLock           |  |
       |  +---------+----------+         +----------------------+  |
       |            |                                              |
       |            | Loopback Control Channel (127.0.0.1:8766)    |
       |            | AUTH <token> -> START / STOP / STATUS / QUIT |
       |            v                                              |
       |  +-----------------------------------------------------+  |
       |  | Python Supervisor (server/embedded_entry.py)        |  |
       |  | - Single asyncio event loop (Process Singleton)     |  |

       |  |                                                     |  |
       |  |   +----------------------------------------------+  |  |
       |  |   | GameServer (server/main.py)                  |  |  |
```

## 2. Component Layers

### 2.1 Game Engine (`engine/`)
- Pure Python 3.12 core containing game state machines, word repository, validation, and secrecy filtering.
- Implements custom fundamental data structures (`engine/structures/`):
  - `CircularLinkedList`: Manages turn orders and player clue cycles ($O(1)$ cycle step).
  - `MinHeap`: Manages scheduled game timers and discussion/voting deadlines ($O(\log N)$ extraction).
  - `Queue`: Manages asynchronous action execution pipelines ($O(1)$ FIFO).
  - `ChainedHashTable`: Manages active room registry with djb2 hashing ($O(1)$ lookup/insert).
- Guarantees strict role and word secrecy (crew views never see the impostor identity until round ends; impostor views never see secret word before round ends).

### 2.2 WebSocket Game Server (`server/main.py`)
- Built on `websockets` (17.3 pure-Python wheel).
- Maintains active rooms, client connection tracking, heartbeats, and 100ms ticker loop.
- Supports dynamic clean shutdown (`stop()`):
  - Broadcasts `room_closed` to all active clients.
  - Closes all connected websockets concurrently with code `1000`.
  - Cancels background ticker task and per-connection handler tasks.
  - Clears `RoomRegistry` hash table and room locks.
  - Closes the server socket (`server.close()` + `server.wait_closed()`), releasing port `8765`.

### 2.3 Embedded Python Supervisor (`server/embedded_entry.py`)
- Acts as a long-lived supervisor daemon running inside the Android process via `serious_python`.
- **Process Singleton**: Because CPython cannot be re-initialized inside the same Android process (`Py_Initialize()` called once, `SeriousPython.terminate()` is a no-op), the supervisor runs continuously for the lifetime of the process.
- **Loopback Control Channel**:
  - Bound exclusively to `127.0.0.1:8766` (`EMBEDDED_CONTROL_PORT`).
  - Completely unreachable from outside the host device.
  - Authenticated via cryptographically random token (`EMBEDDED_CONTROL_TOKEN`) generated by Dart at launch.
  - Commands:
    - `START [port]`: Starts `GameServer` on `0.0.0.0:port` (default 8765).
    - `STOP`: Gracefully stops `GameServer`, disconnects clients with `room_closed`, and releases port 8765. Idempotent.
    - `STATUS`: Returns JSON status: `{"status": "OK", "running": bool, "port": int?, "rooms": int, "connections": int}`.
    - `QUIT`: Shuts down the supervisor loop cleanly.

### 2.4 Flutter Host Application (`app/lib/`)
- **`HostService`**:
  - Manages supervisor lifecycle and control client communication.
  - `ensureServerRunning()`: Launches supervisor if not already running, issues `START 8765`, and polls port until open.
  - `stopServer()`: Issues `STOP` over control channel and polls port until fully released.
  - Integrates with `flutter_foreground_task` and `wakelock_plus` to maintain network and CPU availability during hosting.
  - Hooks into `WidgetsBindingObserver` for `AppLifecycleState.detached` cleanup.
  - **Emergency Fallback**: If `STOP` times out or control channel is unresponsive, invokes `_lastResortFallback()` to stop foreground task and call `exit(1)`.
- **`HostControlClient`**:
  - Lightweight Dart client handling loopback TCP socket connection, token authentication, and command execution (`start`, `stop`, `status`, `quit`).
- **`EmbeddedServerDebugScreen`**:
  - Long-press easter egg on the home screen title.
  - Provides real-time visual inspection of the supervisor and game server status, active connections, and room counts.
  - Allows manual `START` and `STOP` operations with instant port release feedback.

## 4. Milestone 6: Offline Pass & Play Architecture

Milestone 6 introduces a fully offline, single-phone "Pass & Play" mode. Rather than duplicating Python game rules, role distribution, and secrecy logic in Dart, the application reuses the embedded Python server and engine over `127.0.0.1`.

```
+-------------------------------------------------------------------------+
|                  Single Android Device (Airplane Mode / Offline)        |
|                                                                         |
|  +-------------------------------------------------------------------+  |
|  | Pass & Play Setup & Game Screen (Flutter)                         |  |
|  | - Reorderable 3-10 local player names                             |  |
|  | - "Pass the phone to <name>" Interstitials                         |  |
|  | - Privacy lock on AppLifecycleState / orientation changes        |  |
|  +----------------------------------+--------------------------------+  |
|                                     |                                   |
|                      PassAndPlayController (Dart)                       |
|                                     |                                   |
|       +-----------------------------+-----------------------------+     |
|       | Client 0 (Host/P1)          | Client 1 (P2)               | ... |
|       | token: tok_1                | token: tok_2                |     |
|       +--------------+--------------+--------------+--------------+     |
|                      |                             |                    |
|                      +--------------+--------------+                    |
|                                     | Local loopback WebSockets         |
|                                     v (ws://127.0.0.1:8765)             |
|  +-------------------------------------------------------------------+  |
|  | Embedded Python GameServer (server/main.py)                       |  |
|  | - Pure loopback (no Wi-Fi, no camera permissions, airplane ready) |  |
|  | - Spoken Clues Mode (`spoken_clues: true`, `end_turn` action)     |  |
|  | - Strict Engine Secrecy: Each client receives filtered view      |  |
|  | - DSA CircularLinkedList turn rotation & MinHeap timers           |  |
|  +-------------------------------------------------------------------+  |
+-------------------------------------------------------------------------+
```

### 4.1 Multi-Client Controller Model
- `PassAndPlayController` creates and maintains one dedicated `GameClient` instance for each local player ($3 \le N \le 10$).
- Player 0 creates the room (`create_room`), and Players $1 \dots N-1$ join (`join_room`) via `ws://127.0.0.1:8765`.
- **Secrecy Preservation**: The Flutter UI only renders the view of the player who currently holds the phone (`activePrivateClient.state`). The Python engine's secrecy filters remain the single source of truth.

### 4.2 Spoken Clues & Turn Coordination
- In Pass & Play, players say their clue out loud to avoid giving away clue lengths or typing awkwardly on a shared screen.
- When `spoken_clues` is enabled in `GameSettings`:
  - `turn_timer_seconds` defaults to `0` (untimed turns, though timers can still be configured).
  - A player ends their turn using the `end_turn` WebSocket action.
  - The engine logs `[spoken]` as the clue placeholder and advances `_turn_order.next()` via `CircularLinkedList`.
  - Typed `submit_clue` calls are rejected with an error frame.

### 4.3 Privacy & Interstitial Safety
- **Pass-the-Phone Gate**: All private phases (`ROLE_REVEAL`, `VOTING`, `IMPOSTOR_GUESS`) display `PassThePhoneWidget` ("Pass the phone to <Name>") with an explicit "I am <Name>" button before revealing secret cards or ballots.
- **Hold-to-Reveal**: Role reveals require continuous touch-and-hold; releasing hides the card.
- **Lifecycle & Rotation Locking**: Registered `WidgetsBindingObserver` callbacks call `lockPrivateContent()` whenever the application loses focus, enters the background, or changes orientation/metrics.
- **PopScope Back-Button Guard**: Prevents accidental exit during private and shared screens, requiring confirmation before terminating the local session.

## 5. Network & Security Considerations

1. **Loopback Isolation**:
   - The control port (`8766`) is strictly bound to `127.0.0.1`. Attempts to connect from external network interfaces are rejected at the OS network stack level.
   - In Pass & Play mode, all game traffic is exclusively routed through loopback `127.0.0.1:8765`, operating with zero external network connectivity (fully functional in Airplane Mode).
2. **Token Authentication**:
   - Every control command requires matching the 256-bit hexadecimal token generated dynamically by the host application on process startup.
3. **Game Server Scope**:
   - When hosting Wi-Fi games, the game server (`8765`) binds to `0.0.0.0` to permit LAN multiplayer connections, but exposes only the sanitized Impostor WebSocket protocol (`engine/protocol.py`).
4. **Idempotency & Resilience**:
   - All supervisor and engine teardown operations are idempotent and fail-safe. If clients close unexpectedly or network drops, internal tables and tasks are safely reclaimed.
